# ZBSwork × Octop 总体方案与架构

> 版本：2026-10-08（规范化版）· 维护：总控 · 本文是**唯一**的总体方案；旧 WorkBuddy 体系已归档（见 [迁移说明](迁移说明.md)）。
> 标注：【实测】命令验证 ·【源码】读代码 ·【决定】用户已确认 ·【待定】需用户裁决。
> 生产现状、配置、证书、决策等内部信息在私有库 `ZBSwork-OCTOP-service/docs/`，本公开文档不记录。

## 1. 目标与唯一硬约束

**用上游 Octop 官方版本 + 本期需求，构建新版本部署到 Docker；以后跟着上游持续升级。**【决定】

- 不追求和当前生产镜像一模一样；旧 AI 构建的版本、改动位置、新增功能**一律不作参考**。
- **唯一硬约束：真实用户数据不丢、不坏。** 任何切换都先快照、可回退（见 §9）。

## 2. 核心思路：配方，而不是分叉

```
上游 Octop 源码（UPSTREAM.lock 锁定的 tag）
   + patches/  按编号顺序打补丁（只放必须改源码的极少数改动）
   + brand/    品牌包（定稿 logo + 文字规则，脚本应用，不手改）
   = 施工树 → Docker 镜像（服务端 + 网页端） / EXE·DMG（桌面端，直连公司服务器）
```

上游发新版：只改 `UPSTREAM.lock` → `tools/prepare.py` 实测 → 哪个补丁冲突只修哪个。

## 4. 功能分层（新需求先判层，越靠前越好）

| 层 | 含义 | 升级成本 | 放哪里 | 后期需求的预判 |
|---|---|---|---|---|
| **L0** 配置 | 管理后台 / `config.json` 就能做 | 零 | service 库配置台账 | 生图/生视频模型接入（全员统一时） |
| **L1** 插件 | 上游扩展机制（tool / skill / hook / MCP） | 低 | 独立库 `ZBSwork-octop-plugin-<功能>` | 知识库检索增强、按用户限模型（先评估能否用 hook 实现） |
| **L3** 外部服务 | 独立进程/容器，经 MCP 或 HTTP 对接 | 低 | 独立库 | 文件管理 `localoctop`（已在运行） |
| **L2** 核心补丁 | 必须改上游源码 | 高 | 本库 `patches/` | 只在 L0/L1/L3 都做不到时 |

判层顺序 L0 → L1 → L3 → L2。进 L2 的任务书必须写明“为什么前三层做不到”。

## 5. 隔离规则：功能之间不互相乱改、不拖垮主服务

| # | 规则 | 怎么保证 |
|---|---|---|
| 1 | 一个功能只占一个位置：一个补丁目录，或一个独立库 | `modules.yaml` 登记；CI 检查“未登记目录” |
| 2 | **同一上游文件只能有一个主人模块**；确需共改，在 `modules.yaml` 的 `shared_files` 登记主人、允许共改者和理由 | CI `tools/check_ownership.py`，未登记即失败 |
| 3 | 每个补丁在“上游 + 前序补丁”上严格应用；全部叠加后品牌校验 CLEAN | CI `prepare.py`（锁定版本 + 下一个上游版本两套） |
| 4 | 插件 / 外部服务**不改上游源码、不改上游数据表**；自建表加 `zbs_` 前缀，迁移脚本可回退 | 评审检查项（PR 模板） |
| 5 | 插件 / 外部服务独立运行（独立容器、端口、超时），挂了只影响自己 | 部署模板分开（service 库 `deploy/<服务>/`） |
| 6 | 新功能默认关闭，用开关启用；先影子环境验收再上生产 | 任务书验收项 |
| 7 | 一个任务一个分支一个 PR；PR 只改自己模块的目录；跨模块改动拆成多个 PR | 分支保护 + 评审 |

## 6. 编号与命名

| 对象 | 规则 | 例 |
|---|---|---|
| 补丁目录 | `NN-类别-英文名`；10–19 修复(fix)、20–49 功能(feat)、50–59 桌面(desk)、60–69 服务端/镜像(svc) | `52-desk-server-url` |
| 退役编号 | 不复用（20、50、51 已退役；新桌面模块从 52 起） | — |
| 发布 tag | `v<上游版本>-zbs<n>`，n 只增不减；zbs1、zbs2 已归档，新体系从 **zbs3** 起 | `v1.0.2b6-zbs3` |
| 插件库 | `ZBSwork-octop-plugin-<功能>` | `ZBSwork-octop-plugin-kb` |
| 归档 tag | `archive/<年-月>/<说明>`，只读，永不删除 | `archive/2026-10/build-init` |

## 9. 部署与迁移（可迁移、可长期运行）

- **一个镜像通用**：镜像是 `linux/amd64`，Windows Docker Desktop、Linux 服务器、Windows Server 上的 Linux 虚拟机都能运行。
  Windows Server 建议用 Hyper-V 跑 Linux 虚拟机再装 Docker Engine（Docker Desktop 不支持服务器版 Windows）。
- **镜像仓库**：GHCR（`ghcr.io/byronz1z/...`），与代码同账号，不另配密钥。【决定】
- **生产只拉镜像**：compose 只写 `image:`，不再在生产机上从源码构建。迁移服务器 = 拷贝 compose + `.env` + 证书 + 两份数据（PG 数据、Octop 数据卷）。
- **数据安全**（唯一硬约束）：
  1. 切换前快照：PG 导出 + 数据卷打包 + 当前 `config.json` + 当前镜像 tag，带 hash；
  2. 影子验证：新镜像连快照副本，不连生产库；
  3. 切换；4. 24 小时对账（用户数、智能体数、关键功能）。
  - ⚠ 新版本启动时可能升级数据库结构【源码 b6：`src/octop/infra/db/migrate.py`，版本记在 `_schema_version` 表】。结构升级后，**仅把镜像改回旧版不一定能回退**，回退以“恢复快照”为准。
