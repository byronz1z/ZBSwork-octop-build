# ZBSwork × Octop 总体方案与架构

> 版本：2026-10-08 · 维护：总控 · 本文是**唯一**的总体方案；旧 WorkBuddy 方案已归档（见 [迁移说明](迁移说明.md)）。
> 标注约定：【实测】本轮命令验证 ·【源码】读代码得出 ·【决定】用户已确认 ·【待定】需用户裁决

## 1. 一句话目标

**跟着上游 Octop 持续升级，同时保住 ZBSwork 的品牌和少量定制。**
不追求“复现当前生产版本”——当前生产正常运行，只需在下一次升级时换成本体系产出的镜像/安装包。

## 2. 核心思路：配方，而不是分叉

```
上游 Octop 源码（某个 tag）
   + patches/  按编号顺序打补丁（只放必须改源码的少量改动）
   + brand/    品牌包（logo 素材 + 文字规则，脚本应用，不靠手改）
   = 构建树 → Docker 镜像（服务端+网页端） / EXE·DMG（桌面云壳）
```

- 上游发新版时：只改 `UPSTREAM.lock` 的 tag → `tools/prepare.py` 实测 → 哪个补丁冲突就只修哪个。
- 补丁越少越好：能用后台配置（L0）、插件（L1）、外部服务（L3）解决的，**不进**补丁。
- 品牌是数据，不是代码：`brand/brand.yaml` 列清每个 logo 槽位和每条文字替换；上游改了原文，`check.py` 会直接报出来。

【实测 2026-10-08】当前 4 个启用补丁 + 品牌包在上游 **v1.0.2b4 与 v1.0.2b6 上都能严格应用**，品牌校验 CLEAN，
“模型分用户”验收 24/24 通过 —— 也就是说 b4→b6 升级几乎零成本。

## 3. 功能分层（新需求先判层，越靠前越好）

| 层 | 含义 | 升级成本 | 放哪里 | 已知需求归类 |
|---|---|---|---|---|
| **L0** 后台配置 | 管理后台/`config.json` 就能做到 | 零 | service 库运维台账 | 生图/生视频模型接入（全实例统一）；上传上限 300MB；自动备份开关 |
| **L1** 插件 | 上游插件机制（tool / skill / hook / 聊天卡片） | 低（接口稳定即可） | 独立库 `ZBSwork-octop-plugin-<名>` | 文件管理增强、知识库检索增强（待评估） |
| **L3** 外部服务 | 独立进程/容器，通过 MCP 或 HTTP 对接 | 低 | 独立库 | `localoctop`（本地文件桥，已在跑 0.6.1） |
| **L2** 核心补丁 | 必须改上游源码 | 高（每次升级都可能冲突） | 本库 `patches/` | PG 修复、模型分用户、桌面云壳、镜像依赖 |

判层顺序：L0 → L1 → L3 → L2。**L2 是最后手段**，进 L2 的需求必须在任务里写明“为什么 L0/L1/L3 做不到”。

## 4. GitHub 仓库布局（云端）

```
github.com/byronz1z/
├── ZBSwork-octop                    公开 · 上游纯镜像（fork of TencentCloud/Octop）
│   ├── main                         只做 ff-only 快进同步上游，永不提交自有改动
│   ├── v1.0.2b1 … v1.0.2b6          上游 tag 原样同步
│   ├── archive/2026-10/*            7 个归档 tag：旧分支/旧发布的永久指针（只读）
│   └── pr/<主题>                    （按需）给上游提 PR 的分支，例：pr/pg-bootstrap-marker
│
├── ZBSwork-octop-build              公开 · 配方库（本库）★ 日常工作都在这里
│   ├── main                         受保护：只通过 PR 合入，CI 必须通过
│   ├── feat/<名> fix/<名>            施工分支（编码 agent 在此工作）
│   ├── upgrade/<上游版本>            升级分支，例：upgrade/v1.0.2b6
│   └── tag v<上游版本>-zbs<n>        发布点，例：v1.0.2b4-zbs3（下一个可用号）
│
├── ZBSwork-OCTOP-service            私有 · 部署与运维（含生产地址、台账，不含明文密钥）
│
├── localoctop                       公开 · L3 外部服务：本地文件桥
│
└── ZBSwork-octop-plugin-<功能>       （未来）一个插件一个库，公开或私有逐个定
```

**为什么配方库公开、service 私有**【决定】：
上游本身开源（MIT 许可，【源码】`LICENSE`），补丁和品牌素材公开没有额外风险；MIT 只要求保留原版权声明——品牌替换只改界面显示名，不动 `LICENSE`，合规。生产地址、运维台账、决策记录属于内部信息，放私有库。
密钥**任何库都不放**：只放 `.env.example` 占位，真实值留在生产机 `.env` 与离线备份。

**zbs 序号说明**：`zbs1`、`zbs2` 已被旧体系用过（已降为归档），为避免混淆，新体系从 **`zbs3`** 起。

### 补丁编号段（为以后的功能留位置）

| 编号段 | 类别 | 目录名前缀 | 现有 | 未来示例 |
|---|---|---|---|---|
| 10–19 | 修复 fix | `1x-fix-` | 10 PG 修复 | 上游 bug 的临时修复（提 PR 后退役） |
| 20–49 | 功能 feat | `2x-feat-` … `4x-feat-` | 20 模型分用户 | 30 文件管理改造、35 知识库改造（**仅当插件做不到时**） |
| 50–59 | 桌面端 desk | `5x-desk-` | 50 云壳、51 窗口拉伸 | 自动更新、开机自启策略 |
| 60–69 | 服务端/镜像 svc | `6x-svc-` | 60 依赖 | 镜像体积优化、健康检查 |

功能较大时可以在编号段内拆成多个补丁（例：`30-feat-filemgr-api`、`31-feat-filemgr-ui`），按编号顺序应用。

### 三类 logo 槽位（品牌包）

| 槽位 | 母本 | 落到上游哪里 | 在界面哪里出现 |
|---|---|---|---|
| 方形 square | `icon.svg` / `icon-1024.png` | `favico.svg`、`apple-touch-icon.png`、`pwa-192/512.png`、桌面 `appicon.png`、`tray-icon.png` | 浏览器标签、PWA 安装图标、侧栏收起时、EXE 图标、托盘 |
| 横版 horizontal | `brand-horizontal.svg` | `logo_horizontal_dark.png`（浅色主题）/ `_white.png`（深色主题） | 侧栏顶部、移动端页头、登录页、初始化页 |
| 竖版 vertical | `brand-vertical.svg` | `logo_vertical_dark.svg`（浅色主题）/ `_white.svg`（深色主题） | 网页启动闪屏、离线页 |

【实测缺陷】竖版深色主题变体与浅色变体**完全相同**（文字色 `#231815` 近黑）→ 深色主题启动闪屏上文字可能看不见。需要补一张白字竖版素材。

## 7. 交付形态

| 形态 | 来源 | 产物 | 状态 |
|---|---|---|---|
| **Service**（Docker） | 配方 → 构建镜像 | `octop` 镜像（服务端 + 网页端） | 生产在跑 `octop:pg-1.0.2b4-r2`（旧线产物）；新体系镜像待首次构建 |
| **Desk**（EXE / DMG） | 配方（含 50 号补丁）→ Wails 构建 | Windows 64 位 exe、macOS dmg | 在用 `ZBSwork 1.0.2b2`（旧线 `zbswork-brand@366560cf`，归档 tag 永久保留）；新体系安装包待首次构建 |

**桌面端是纯云壳**【源码】：EXE 不在本地运行 Octop 服务，只用内置地址打开公司服务器网页；
唯一的网络请求是健康检查。这是 50 号补丁的定制，**不是上游原生行为**。

## 9. 发布流程（目标态，首次执行时按任务落地）

1. 配方库 `main` 通过 CI → 打 tag `v<上游>-zbs<n>`。
2. 构建 workflow（待建，见任务清单）按 tag：prepare → 构建镜像推 `ghcr.io/byronz1z/...`（或 Docker Hub，【待定】）→ 构建 exe/dmg 挂 Release。
3. service 库改 `deploy/` 中的 `image:tag` → 生产按四步切换：快照 → 影子验证 → 指针切换 → 24h 对账。
4. 切换失败：`image:tag` 改回上一版即可回滚（数据卷与 PG 不动）。
