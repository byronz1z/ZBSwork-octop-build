# 协作规范（新任务一律按此执行）

> 版本：2026-10-08。旧体系（认知纲领 / 流转六纪律 / 任务台账 T-001…）已归档，**不再使用**。
> 原则只有三条：**事实有证据、任务有载体、合入有门禁。**

## 1. 角色

| 角色 | 谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 决策人 | 用户 | 确认需求、裁决待定项、最终验收 | — |
| 总控 | 主 AI 会话 | 判层（L0–L3）、拆任务、写任务书、审 PR、核对证据、维护文档 | 不替用户做业务决定；不把推断写成事实 |
| 施工方 | 编码 agent（任意模型）或人 | 在施工分支按任务书改代码、跑验证、提 PR | 不改任务范围；不直接推 main |
| 门禁 | GitHub Actions `recipe-check` | 客观检查：补丁可应用、品牌 CLEAN、验收脚本通过 | — |

多个 agent 并行时：**一个任务一个分支一个 PR**，写入的文件范围互不重叠；总控负责排序与合并冲突。

## 2. 任务载体：GitHub Issues

| 事项性质 | 开在哪个库 |
|---|---|
| 品牌、补丁、升级、构建、插件评估（可公开） | `ZBSwork-octop-build` |
| 生产部署、运维、证书、密钥、生产数据（敏感） | `ZBSwork-OCTOP-service`（私有） |
| 某个插件内部的开发 | 该插件自己的库 |

任务书用模板 `.github/ISSUE_TEMPLATE/task.yml`，必须写：类型、层级、目标（用户原话）、范围（含“明确不改什么”）、验收标准。

### 状态标签（流转）

```
状态:待确认 ──用户确认──▶ 状态:已确认 ──施工方认领──▶ 状态:施工中 ──提 PR──▶ 状态:待验收
                                                                                │
                                         ┌─────────────验收通过──────────────────┤
                                         ▼                                       ▼
                                   状态:已完成（关闭）                     状态:驳回（写原因，回到施工中或关闭）
```

- “待确认”：总控写的任务书，用户没点头前**不得施工**。
- “已完成”：必须附证据（CI 链接 / 命令输出 / 截图），没有证据的完成不算完成。
- 生产相关任务额外标签 `生产:只登记`，表示需用户授权窗口后才能执行。

## 3. 分支与命名

| 对象 | 规则 | 例 |
|---|---|---|
| 施工分支 | `feat/<名>`、`fix/<名>`、`brand/<名>`、`docs/<名>` | `feat/filemgr-plugin-eval` |
| 升级分支 | `upgrade/<上游 tag>` | `upgrade/v1.0.2b6` |
| 补丁目录 | `NN-类别-英文名`（编号段见总体方案 §5） | `30-feat-filemgr-api` |
| 发布 tag | `v<上游版本>-zbs<n>`，n 递增不回退 | `v1.0.2b6-zbs3` |
| 上游 PR 分支（在 fork 库） | `pr/<主题>` | `pr/pg-bootstrap-marker` |
| 插件库 | `ZBSwork-octop-plugin-<功能>` | `ZBSwork-octop-plugin-filemgr` |

禁止：`V1/V2/final/new` 这类平行命名；在 fork 的 `main` 上提交自有改动。

## 4. 三条标准流程

### 4.1 上游升级（例：b4 → b6）

1. 开任务（类型=上游升级）→ 开分支 `upgrade/v1.0.2b6`。
2. 改 `UPSTREAM.lock`：`tag`/`commit` 换成新版本，`next_target` 指向再下一个（没有就删）。
3. `uv run --with pyyaml tools/prepare.py`：
   - 全 OK → 跳到第 5 步；
   - 某补丁 FAIL → 只修这个补丁（见 4.2 的第 3–5 步），其余不动；
   - `brand/check.py` 报“规则未命中” → 上游改了原文，更新 `brand/brand.yaml` 对应条目。
4. 读上游 changelog：有没有已修复我们某个 fix 补丁的问题？有 → 该补丁改 `retired`。
5. 更新 `modules.yaml` 的 `verified` → 提 PR → CI 绿 → 合并 → 打 `v1.0.2b6-zbs<n>`。

### 4.2 新功能

1. **判层**（总控）：L0 后台配置能做吗？→ L1 插件能做吗？→ L3 外部服务能做吗？→ 都不行才 L2。
   任务书里写明判层理由。
2. L0：写进 service 库运维台账，完成。L1/L3：新建独立库，按该库自己的流程。
3. L2：在 `modules.yaml` 登记新条目（`status: candidate`）+ 建 `patches/NN-feat-<名>/README.md`。
4. 施工：`tools/prepare.py`（得到 上游+现有补丁+品牌 的施工树）→ 在 `.work/src` 里 `git add -A && git commit -m base`
   → 改代码 → `git commit` → `tools/export.py --module NN-feat-<名> --base <base 那次提交>`。
   （注：导出时要排除品牌改动——在 `--no-brand` 的施工树上施工即可。）
5. 写验收脚本放 `patches/NN-.../verify/`，并加进 CI。
6. `status` 改 `enabled` → PR → CI 绿 → 用户验收 → 合并。

### 4.3 品牌调整

- 换 logo：替换 `brand/assets/` 下对应文件（母本 + 成品），不改 `brand.yaml`。
- 新增要替换的文字：在 `brand.yaml` 的 `text:` 加一条“精确原文 → 新文”。
- 跑 `brand/check.py --self` 与 `tools/prepare.py`，CLEAN 才能提 PR。

## 5. 证据规范

| 结论类型 | 合格证据 | 不合格 |
|---|---|---|
| 补丁可用 | `prepare.py` 输出 / CI 链接 | “应该能打上” |
| 功能可用 | 验收脚本 N/N 通过；或构建产物 + 实机截图 | “代码已改完” |
| 生产状态 | 当次只读命令输出（带日期） | 引用旧快照 |
| 上游行为 | 指向 tag + 文件 + 行号 | “上游原生就这样” |

文档与回复中标注：【实测】【源码】【决定】【推断】【待定】。密钥一律写 `[REDACTED]`。

## 6. 生产操作边界

- PC130 生产机：总控只做**只读**查询；任何写操作（重启、改配置、换镜像、删文件）必须有 service 库任务 + 用户明确授权。
- 切换镜像四步：① 快照（PG dump + 数据卷 + 当前镜像）→ ② 影子验证（新镜像连副本库）→ ③ 改 `image:tag` 切换 →
  ④ 24 小时对账（用户数、agent 数、关键功能）。任一步失败回滚到上一 `image:tag`。
