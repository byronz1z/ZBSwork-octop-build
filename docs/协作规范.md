# 协作规范（新任务一律按此执行）

> 版本：2026-10-08（规范化版）。旧体系（认知纲领 / 流转六纪律 / 任务台账 T-001…）已归档，**不再使用**。
> 三条原则：**事实有证据、任务有载体、合入有门禁。**

## 1. 角色

| 角色 | 谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 决策人 | 用户 | 确认需求、裁决待定项、最终验收 | — |
| 总控 | 主 AI 会话 | 判层、拆任务、写任务书、审 PR、核对证据、维护文档 | 不替用户做业务决定；不把推断写成事实；不扩大范围 |
| 施工方 | 编码 agent（任意模型）或人 | 在施工分支按任务书改代码、跑验证、提 PR | 不改任务范围；不直接推 main；不碰生产 |
| 门禁 | GitHub Actions `recipe-check` | 客观检查：模块登记、模块隔离、品牌 CLEAN、补丁可应用 | — |

多个 agent 并行：**一个任务一个分支一个 PR**，各自只写自己模块的目录；写入范围重叠的任务不得并行，由总控排序。

## 2. 任务载体：GitHub Issues

| 事项性质 | 开在哪个库 |
|---|---|
| 品牌、补丁、升级、构建发布、插件评估（可公开） | `ZBSwork-octop-build` |
| 生产部署、运维、证书、密钥、生产数据（敏感） | `ZBSwork-OCTOP-service`（私有） |
| 文件管理（localoctop）开发 | `localoctop` |
| 某个插件的开发 | 该插件自己的库 |

任务书用模板 `.github/ISSUE_TEMPLATE/task.yml`：类型、层级、目标（用户原话）、范围（含**明确不改什么**）、验收标准。

### 标签

| 标签 | 含义 |
|---|---|
| `状态:待确认` → `状态:已确认` → `状态:施工中` → `状态:待验收` → `状态:已完成` | 主流程；`状态:驳回` 写原因后回到施工中或关闭 |
| `生产:只登记` | 涉及生产机写操作；只登记，用户给出授权窗口后才执行 |
| `期:第一期` / `期:后期` | 范围；`期:后期` 的任务本期不得施工 |

- `待确认` 的任务，用户没点头前**不得施工**。
- `已完成` 必须附证据（CI 链接 / 命令输出 / 截图）。没有证据不算完成。

## 3. 分支与命名

| 对象 | 规则 | 例 |
|---|---|---|
| 施工分支 | `feat/`、`fix/`、`brand/`、`desk/`、`docs/` + 名字 | `brand/locales-full` |
| 升级分支 | `upgrade/<上游 tag>` | `upgrade/v1.0.2b6` |
| 补丁目录 / 编号段 / 发布 tag / 插件库 | 见 [总体方案 §6](总体方案与架构.md) | — |
| 上游 PR 分支（在 fork 库） | `pr/<主题>` | `pr/pg-bootstrap-marker` |

禁止：`V1/V2/final/new` 式平行命名；在 fork 的 `main` 上提交自有改动；复用已退役编号。

## 4. 标准流程

### 4.1 上游升级（例：b4 → b6）

1. 开任务 → 分支 `upgrade/v1.0.2b6`。
2. 改 `UPSTREAM.lock`：`tag`/`commit` 换新版本；`next_target` 指向再下一个（没有就删）。
3. `uv run --no-project --with pyyaml tools/prepare.py`：
   - 全 OK → 第 5 步；
   - 某补丁失败 → 只修这一个（按 4.2 第 4 步重新导出），其余不动；
   - 品牌报“规则未命中” → 上游改了原文，更新 `brand/brand.yaml` 对应条目。
4. 读上游更新日志：上游是否已修复我们某个修复补丁的问题？是 → 该模块退役。
5. 更新 `modules.yaml` 的 `verified` → PR → CI 绿 → 合并 → 打 `v<上游>-zbs<n>`。
6. 生产切换走 service 库任务（快照 → 影子 → 切换 → 24 小时对账）。

### 4.2 新功能（后期）

1. **判层**（总控）：L0 配置 → L1 插件 → L3 外部服务 → L2 核心补丁。任务书写明判层理由。
2. L0：记入 service 库配置台账，完成。L1 / L3：新建独立库，按 [总体方案 §5](总体方案与架构.md) 隔离规则开发。
3. L2：
   1. `modules.yaml` 登记（`status: candidate`）+ 建 `patches/NN-类别-名/README.md`（写清改哪些上游文件）；
   2. 若要改的文件已有主人模块：先在 `shared_files` 登记并说明理由，否则 CI 不过；
   3. 施工：`tools/prepare.py --no-brand --until <本模块> --commit-base` 得到施工树和 `BASE=<sha>` → 改代码 → 提交
      → `tools/export.py --module <本模块> --base <sha>`；
   4. 写验收脚本放 `patches/NN-.../verify/` 并加进 CI；
   5. `status` 改 `enabled` → PR → CI 绿 → 用户验收 → 合并。
4. 新功能默认关闭（开关）；上生产前在影子环境验收。

### 4.3 品牌调整

- 换 logo：先换定稿目录（见总体方案 §10）→ 同步到 `brand/assets/source/` → 重新生成成品图。不得使用 `过程稿-停用\` 里的文件。
- 新增要替换的文字：在 `brand/brand.yaml` 的 `text:` 加精确替换规则，不用全局正则。
- 每次改动后 `brand/check.py` 必须 CLEAN。

## 5. 证据规则

| 结论类型 | 必须附 | 不接受 |
|---|---|---|
| 补丁可用 | `prepare.py` 输出 / CI 链接 | “应该能打上” |
| 功能可用 | 验收脚本 N/N 通过；或构建产物 + 实机截图 | “代码已改完” |
| 生产状态 | 当次只读命令输出（带日期） | 引用旧快照 |
| 上游行为 | 指向 tag + 文件 + 行号 | “上游原生就这样” |

文档与回复中标注：【实测】【源码】【决定】【推断】【待定】。密钥一律写 `[REDACTED]`。

## 6. 生产操作边界

- 生产机：总控只做**只读**查询；写操作（重启、改配置、换镜像、删文件）必须有 service 库任务 + 用户明确授权。
- 唯一硬约束是**用户数据不丢不坏**。切换四步：① 快照（PG 导出 + 数据卷 + `config.json` + 当前镜像 tag，带 hash）
  → ② 影子验证（新镜像连快照副本）→ ③ 切换 → ④ 24 小时对账（用户数、智能体数、关键功能）。
- 新版本可能升级数据库结构：回退以“恢复快照”为准，不能只改回旧镜像 tag。

## 7. 构建与发布（第一期待建）

当前门禁只校验配方，不构建产物。第一期新增 `release.yml`：tag 触发 → prepare → 构建镜像推 GHCR + 构建 EXE/DMG
→ 挂 GitHub Release（验收通过前为草稿）。在此之前生产继续运行现有镜像，员工继续用在用 EXE。
